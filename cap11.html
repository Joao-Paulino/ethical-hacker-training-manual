3. Invoke-AtomicRedTeam Original

O projeto Atomic Red Team foi desenvolvido pela Red Canary para fornecer testes pequenos e focados que mapeiam diretamente para técnicas reais de adversários. O Invoke-AtomicRedTeam é um módulo PowerShell que permite executar esses testes diretamente de um sistema Windows. Cada teste corresponde a uma técnica do framework MITRE ATT&CK, e todos estão armazenados na chamada pasta atomics. Dentro dessa pasta, encontras um diretório para cada técnica, identificado pelo seu número T. Dentro de cada diretório, há ficheiros YAML que descrevem como o ataque funciona, o que requer e o que faz, juntamente com uma versão markdown mais legível para humanos. The Atomic Red Team project was developed by Red Canary to provide small, focused tests that map directly to real adversary techniques. Invoke-AtomicRedTeam is a PowerShell module that allows you to execute these tests directly from a Windows system. Each test corresponds to a technique from the MITRE ATT&CK framework, and all of them are stored in the so-called atomics folder. Inside this folder, you will find a directory for each technique, identified by its T-number. Within each of those directories, there are YAML files that describe how the attack works, what it requires, and what it does, along with a more readable markdown version for humans.

5. Instalação Original

Há várias formas de instalar o Invoke-AtomicRedTeam, mas uma das mais rápidas é fornecida diretamente na documentação oficial. É importante compreender que isto requer privilégios administrativos e, em muitos casos, as proteções antivírus terão de ser desativadas na máquina de teste. Por isso, nem todos os sistemas são adequados para executar estes testes. A abordagem recomendada é usar uma máquina de teste dedicada ligada ao teu SIEM e stack de monitorização de segurança. Isso permite observar alertas, logs e deteções sem arriscar sistemas de produção. There are several ways to install Invoke-AtomicRedTeam, but one of the quickest methods is provided directly in the official documentation. It is important to understand that this requires administrative privileges and, in many cases, antivirus protections will need to be disabled on the test machine. Because of this, not every system is suitable for running these tests. The recommended approach is to use a dedicated testing machine connected to your SIEM and security monitoring stack. This allows you to observe alerts, logs, and detections without risking production systems. 
PS > IEX (IWR 'https://raw.githubusercontent.com/redcanaryco/invoke-atomicredteam/master/install-atomicredteam.ps1' -UseBasicParsing);
PS > Install-AtomicRedTeam -getAtomics -Force
O processo de instalação pode demorar algum tempo, pois descarrega os ficheiros necessários e prepara o ambiente de teste. The installation process can take some time, as it downloads the necessary files and prepares the testing environment.

6. Técnicas Original

Após a instalação, tens acesso a uma vasta gama de técnicas MITRE ATT&CK. Cada técnica pode incluir múltiplas sub-técnicas, dependendo do sistema operativo. Podes explorar todas em detalhe e listar sub-técnicas disponíveis com um comando simples: Once installation is complete, you have access to a wide range of MITRE ATT&CK techniques. Each technique may include multiple sub-techniques, depending on the operating system. You can explore them all in detail, and list available sub-techniques with a simple command: 
PS > Invoke-AtomicTest T1012 -ShowDetailsBrief
Para uma visão mais profunda do que uma sub-técnica específica faz, podes pedir detalhes completos: For deeper insight into what a specific sub-technique does, you can request full details: 
PS > Invoke-AtomicTest T1003-3 -ShowDetails
Se uma deteção falhar ou nenhum alerta for acionado, podes entregar os comandos exatos e referências de técnicas aos defensores para melhorarem as suas regras e visibilidade. If a detection fails or no alert is triggered, you can hand over the exact commands and technique references so defenders can improve their rules and visibility.

7. Pré-requisitos Original

Alguns testes atómicos requerem pré-requisitos específicos. Isto pode incluir software, alterações de configuração ou ferramentas que devem estar presentes no sistema. Um exemplo comum é o PDQ Deploy, uma ferramenta legítima de deployment de software usada por administradores para empurrar atualizações em grandes ambientes Windows. O PDQ Deploy é poderoso e, como muitas ferramentas administrativas, pode tornar-se perigoso nas mãos erradas. Foi abusado por grupos de ransomware como o LockBit para distribuir payloads maliciosos em redes inteiras. Isto não é exclusivo do PDQ Deploy. Group Policy, plataformas de gestão de endpoints e até consolas de gestão de antivírus podem ser transformadas em ferramentas de ataque uma vez comprometidas. Atacantes também recorrem por vezes ao Safe Mode, onde muitas ferramentas de segurança não correm. Ao forçar sistemas a reiniciar em Safe Mode através de alterações de política e executar scripts de shares confiáveis, podem contornar proteções por completo. É por isso que a deteção precoce é o que precisamos. Apanhar um atacante antes de chegar a este estágio pode salvar uma organização de danos generalizados. Some atomic tests require specific prerequisites. This may include certain software, configuration changes, or tools that must be present on the system. A common example is PDQ Deploy, a legitimate software deployment tool used by administrators to push updates across large Windows environments. PDQ Deploy is powerful and, like many administrative tools, can become dangerous in the wrong hands. It has been abused by ransomware groups such as LockBit to distribute malicious payloads across entire networks. This is not unique to PDQ Deploy. Group Policy, endpoint management platforms, and even antivirus management consoles can be turned into attack tools once compromised. Attackers also sometimes rely on Safe Mode, where many security tools do not run. By forcing systems to reboot into Safe Mode through policy changes and executing scripts from trusted shares, they can bypass protections entirely. This is why early detection is what we need. Catching an attacker before they reach this stage can save an organization from widespread damage.
Antes de correr um teste, podes verificar se todos os pré-requisitos estão cumpridos: Before running a test, you can check whether all prerequisites are met: 
PS > Invoke-AtomicTest T1072-2 -CheckPrereqs
Se faltar algo, podes deixar o framework tratar disso: If something is missing, you can let the framework handle it: 
PS > Invoke-AtomicTest T1072-2 -GetPrereqs

8. Testes Original

Uma vez satisfeitos os pré-requisitos, o teste pode começar. Podes correr todas as sub-técnicas de uma técnica com um único comando: Once prerequisites are satisfied, testing can begin. You can run all sub-techniques for a technique with a single command: 
PS > Invoke-AtomicTest T1106
Ou focar-te numa sub-técnica específica: Or focus on a specific sub-technique: 
PS > Invoke-AtomicTest T1106-2
Geralmente é melhor correr os testes individualmente. Isto dá-te mais controlo sobre o que está a ser executado e quando, facilitando a correlação com alertas no SIEM. It is generally better to run tests individually. This gives you more control over what is being executed and when, making it easier to correlate with SIEM alerts.

9. Scripts de Impacto / Impact Scripts Impacto Complementar

Os scripts abaixo ajudam a validar a telemetria gerada pelos testes atómicos, comparando o que foi executado com o que foi registado. São úteis para fechar o ciclo Purple Team. The scripts below help validate telemetry generated by atomic tests, comparing what was executed with what was logged. They are useful for closing the Purple Team loop.

9.1 Script 11.1 — Verificação de Telemetria Pós-Teste / Post-Test Telemetry Check

Objetivo: após correr um teste atómico, verificar se os eventos esperados foram registados (Security, Sysmon, PowerShell). Evidência: telemetry-check.csv. Goal: after running an atomic test, verify that expected events were logged (Security, Sysmon, PowerShell). Evidence: telemetry-check.csv. 
# Script 11.1 - Post-Atomic Telemetry Check
param([int]$MinutesBack = 10)
$out = ".\telemetry-check.csv"
$since = (Get-Date).AddMinutes(-$MinutesBack)
$checks = @()
$sec = Get-WinEvent -LogName Security -MaxEvents 500 -EA SilentlyContinue | Where-Object { $_.TimeCreated -gt $since }
$checks += [PSCustomObject]@{ Source="Security"; EventCount=$sec.Count; LastEvent=($sec | Select-Object -First 1).TimeCreated }
$sys = Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 500 -EA SilentlyContinue | Where-Object { $_.TimeCreated -gt $since }
$checks += [PSCustomObject]@{ Source="Sysmon"; EventCount=$sys.Count; LastEvent=($sys | Select-Object -First 1).TimeCreated }
$ps = Get-WinEvent -LogName "Microsoft-Windows-PowerShell/Operational" -MaxEvents 500 -EA SilentlyContinue | Where-Object { $_.TimeCreated -gt $since }
$checks += [PSCustomObject]@{ Source="PowerShell"; EventCount=$ps.Count; LastEvent=($ps | Select-Object -First 1).TimeCreated }
$checks | Export-Csv $out -NoTypeInformation -Encoding UTF8
Write-Host "[+] Telemetry check -> $out" -ForegroundColor Green
$checks | Format-Table -AutoSize

9.2 Script 11.2 — Correlação de Processos Suspeitos / Suspicious Process Correlation

Objetivo: correlacionar processos criados (4688) com padrões típicos de testes atómicos (PowerShell, cmd, mshta, rundll32). Evidência: process-correlation.csv. Goal: correlate created processes (4688) with typical atomic test patterns (PowerShell, cmd, mshta, rundll32). Evidence: process-correlation.csv. 
# Script 11.2 - Suspicious Process Correlation
$out = ".\process-correlation.csv"
$patterns = @("powershell","cmd\.exe","mshta","rundll32","regsvr32","certutil","bitsadmin")
$hits = @()
Get-WinEvent -LogName Security -MaxEvents 2000 -EA SilentlyContinue |
  Where-Object { $_.Id -eq 4688 } | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $proc = ($xml.Event.EventData.Data | Where-Object Name -eq "NewProcessName").'#text'
    $cmd  = ($xml.Event.EventData.Data | Where-Object Name -eq "CommandLine").'#text'
    foreach ($p in $patterns) { if ($proc -match $p -or $cmd -match $p) { $hits += [PSCustomObject]@{ Time=$_.TimeCreated; Process=$proc; Cmd=$cmd; Pattern=$p } } }
  }
$hits | Export-Csv $out -NoTypeInformation -Encoding UTF8
Write-Host "[+] Process hits: $($hits.Count) -> $out" -ForegroundColor Yellow

9.3 Script 11.3 — Auditoria de Pré-requisitos / Prerequisite Audit

Objetivo: verificar o estado dos pré-requisitos comuns (PDQ Deploy, Sysmon, PowerShell logging) antes de correr testes. Evidência: prereq-audit.csv. Goal: check common prerequisites (PDQ Deploy, Sysmon, PowerShell logging) before running tests. Evidence: prereq-audit.csv. 
# Script 11.3 - Prerequisite Audit
$out = ".\prereq-audit.csv"
$audit = @(
  [PSCustomObject]@{ Item="PDQ Deploy"; Present=(Test-Path "C:\Program Files (x86)\PDQ Deploy") -or (Test-Path "C:\Program Files\PDQ Deploy") }
  [PSCustomObject]@{ Item="Sysmon Service"; Present=($null -ne (Get-Service -Name Sysmon64,Sysmon -EA SilentlyContinue)) }
  [PSCustomObject]@{ Item="Script Block Logging"; Present=((Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -EA SilentlyContinue).EnableScriptBlockLogging -eq 1) }
  [PSCustomObject]@{ Item="Module Logging"; Present=((Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging" -EA SilentlyContinue).EnableModuleLogging -eq 1) }
  [PSCustomObject]@{ Item="AtomicRedTeam folder"; Present=(Test-Path "C:\AtomicRedTeam") }
)
$audit | Export-Csv $out -NoTypeInformation -Encoding UTF8
Write-Host "[+] Prereq audit -> $out" -ForegroundColor Green
$audit | Format-Table -AutoSize

11. Mitigações Blue Team / Mitigations Complementar

  1. Usar máquina de teste dedicada — nunca em produção.
  2. Ligar ao SIEM/EDR — validar que os eventos chegam e disparam regras.
  3. Documentar gaps — se um teste não gerou alerta, criar/ajustar regra.
  4. Desativar AV na máquina de teste — para evitar bloqueio dos testes.
  5. Correr testes individualmente — facilita correlação e troubleshooting.
  6. Verificar pré-requisitos antes de cada teste (Script 11.3).
  7. Fazer cleanup após cada teste (-Cleanup).
  8. Monitorizar PDQ Deploy e ferramentas de deployment — são alvos de abuso.
  9. Detetar Safe Mode abuse — alterações de política que forçam reboot em Safe Mode.
