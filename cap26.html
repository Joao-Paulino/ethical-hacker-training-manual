Understand the three forms of defensive visibility (Process, Command, Network Monitoring); know the critical Event IDs (1101, 4104, 400, 800/4103); understand Sysmon's role; know how defenders correlate telemetry; build native impact scripts for telemetry validation.

2. Contexto e Relevância / Context and Relevance Original

Nenhum sistema é perfeito e nenhuma empresa tem recursos ilimitados. Cada organização em crescimento precisa de analistas constantemente a ajustar alertas e gatilhos de segurança à medida que novo software e utilizadores são adicionados à rede. É trabalho tedioso e repetitivo. Demasiados alertas esgotam até os defensores mais afiados. Fadiga ocular, noites tardias e falsos positivos drenam a atenção. É aí que ganhas uma pequena janela para agir, ou uma chance de passar despercebido. Assumir que ninguém está a ver é um erro de principiante. Vimos muitos principiantes perder acesso a redes inteiras simplesmente porque subestimaram os mecanismos defensivos . No system is perfect and no company has unlimited resources. Every growing organization needs analysts constantly tuning alerts and security triggers as new software and users are added to the network. It's tedious and repetitive work. Too many alerts exhaust even the sharpest defenders. Eye fatigue, late nights, and false positives all drain attention. That's where you get a small window to make a move, or a chance to slip through unnoticed. Assuming nobody is watching is a beginner's mistake. We've seen many beginners lose access to entire networks simply because they underestimated defensive mechanisms .

3. Visibilidade Defensiva Original

Os defensores têm três formas principais de te detetar. Conhecer estas é crucial para sobreviver . Defenders have three main ways to detect you. Knowing these is crucial to survive .

3.1 Process Monitoring

Permite aos defensores acompanhar que programas iniciam, param ou interagem entre si. Cada processo, incluindo PowerShell, deixa rastos da sua origem (parent) e dos seus filhos. Os analistas usam esta linhagem para detetar atividade invulgar. Por exemplo, um processo PowerShell lançado por um documento do Microsoft Word pode ser suspeito. As equipas de segurança usam ferramentas EDR para recolher estes dados, e alguns fornecedores, como a Red Canary, correlacionam-nos com outros eventos para encontrar padrões maliciosos . Allows defenders to keep an eye on what programs start, stop, or interact with each other. Every process, PowerShell included, leaves traces of its origin (parent) and its children. Analysts use this lineage to spot unusual activity. For example, a PowerShell process launched by a Microsoft Word document might be suspicious. Security teams use EDR tools to gather this data, and some providers, like Red Canary, correlate it with other events to find malicious patterns .

3.2 Command Monitoring

Foca-se no que os comandos estão a ser executados dentro do processo. Para PowerShell, isto significa vigiar cmdlets, parâmetros ou comandos codificados específicos. Sozinho, um comando pode parecer inocente, mas em combinação com process monitoring e network telemetry, pode ser um forte indicador de compromisso . Focuses on what commands are being run inside the process. For PowerShell, this means watching for specific cmdlets, parameters, or encoded commands. Alone, a command might look innocent, but in combination with process monitoring and network telemetry, it can be a strong indicator of compromise .

3.3 Network Monitoring

Os atacantes usam frequentemente PowerShell para descarregar ferramentas ou exfiltrar dados pela rede. Monitorizar conexões de saída e entrada é uma forma fiável de os defensores apanharem atividade maliciosa. Um exemplo comum é um comando Invoke-Expression que puxa conteúdo de um servidor externo via HTTP . Attackers often use PowerShell to download tools or exfiltrate data over the network. Monitoring outgoing and incoming connections is a reliable way for defenders to catch malicious activity. A common example is an Invoke-Expression command that pulls content from an external server via HTTP .

4. AMSI — Event ID 1101 Original

AMSI significa Antimalware Scan Interface. Pensa nisto como um checkpoint de segurança dentro do Windows que vigia scripts a correr em memória, incluindo PowerShell, VBScript e WMI. O AMSI não armazena logs no Event Viewer padrão. Em vez disso, trabalha com Event Tracing for Windows (ETW), um sistema de logging de nível inferior. Se fizeres bypass do AMSI, podes executar código que normalmente dispararia scans de antivírus, como dump de LSASS ou correr malware, sem deteção imediata. Mas os bypasses de AMSI são arriscados. São frequentemente logados eles próprios, e a Microsoft patcheia-os ativamente. Bypasses públicos são uma armadilha para quem tenta sobreviver discretamente . AMSI stands for Antimalware Scan Interface. Think of it as a security checkpoint inside Windows that watches scripts running in memory, including PowerShell, VBScript, and WMI. AMSI doesn't store logs in the standard Event Viewer. Instead, it works with Event Tracing for Windows (ETW), a lower-level logging system. If you bypass AMSI, you can execute code that normally would trigger antivirus scans, like dumping LSASS or running malware, without immediate detection. But AMSI bypasses are risky. They're often logged themselves, and Microsoft actively patches them. Publicly available bypasses are a trap for anyone trying to survive quietly .

5. ScriptBlock Logging — Event ID 4104 Original

O ScriptBlock logging vigia o código real executado em scripts PowerShell. Há dois níveis: Automático (predefinido) — regista código que parece suspeito, com base na lista da Microsoft de cmdlets perigosos e APIs .NET; Global — regista tudo sem filtros. O Event ID 4104 recolhe esta informação. Podes tentar fazer bypass com downgrade para PowerShell v2, se existir, mas até esse downgrade pode ser logado. É necessária ofuscação subtil . ScriptBlock logging watches the actual code executed in PowerShell scripts. There are two levels: Automatic (default) — logs script code that looks suspicious, based on Microsoft's list of dangerous cmdlets and .NET APIs; Global — logs everything with no filters. Event ID 4104 collects this information. You can try to bypass by downgrading to PowerShell v2, if it exists, but even that downgrade can be logged. Subtle obfuscation is necessary . 
PS > powershell -version 2
Nota / Note:
O ScriptBlock logging só funciona com PowerShell 5 e acima . ScriptBlock logging only works with PowerShell 5 and above .

6. Command-Line Logging — Event ID 400 Original

Mesmo versões mais antigas do PowerShell têm o Event ID 400, que regista quando um processo PowerShell inicia. Não mostra os comandos completos, mas o facto de um processo ter iniciado é registado . Even older PowerShell versions have Event ID 400, which logs when a PowerShell process starts. It doesn't show full commands, but the fact that a process started is noted .

7. Module Logging — Event IDs 800 & 4103 Original

O module logging (Event ID 800) rastreia que módulos PowerShell são carregados, incluindo o código-fonte para comandos executados via Add-Type. Isto é importante porque Add-Type é usado para compilar e executar código C#. No PowerShell 5+, o Event ID 4103 também regista este contexto . Module logging (Event ID 800) tracks which PowerShell modules are loaded, including the source code for commands run via Add-Type. This is important because Add-Type is used to compile and run C# code. In PowerShell 5+, Event ID 4103 also logs this context .

8. Sysmon Original Complementar

O Sysmon é uma ferramenta especializada do Windows que dá aos defensores visibilidade adicional. Os defensores monitorizam tipicamente o Event ID 1 (Process Creation), que regista o processo pai, a linha de comando completa, hashes e GUID do processo. Esta é a base para análise de cadeia de execução, inspeção de linha de comando e threat hunting . Sysmon is a specialized Windows tool that gives defenders additional visibility. Defenders typically monitor Event ID 1 (Process Creation), which logs the parent process, full command line, hashes, and process GUID. This is the foundation for execution chain analysis, command-line inspection, and threat hunting .

9. Scripts de Impacto / Impact Scripts Impacto Complementar

Os scripts abaixo ajudam a validar a telemetria que os defensores veem, e a detetar configurações de logging. The scripts below help validate the telemetry defenders see, and detect logging configurations.

9.1 Script 26.1 — Verificação de Configuração de Logging / Logging Configuration Check

# Script 26.1 - Logging Configuration Check
$out = ".\logging-config.csv"
$checks = [ordered]@{
  "ScriptBlockLogging (4104)" = (Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Name "EnableScriptBlockLogging" -EA SilentlyContinue).EnableScriptBlockLogging
  "ModuleLogging (800/4103)" = (Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging" -Name "EnableModuleLogging" -EA SilentlyContinue).EnableModuleLogging
  "Transcription" = (Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription" -Name "EnableTranscripting" -EA SilentlyContinue).EnableTranscripting
  "Sysmon Service" = [bool](Get-Service -Name Sysmon64,Sysmon -EA SilentlyContinue)
}
$results = foreach ($k in $checks.Keys) { [PSCustomObject]@{ Setting=$k; Value=$checks[$k] } }
$results | Export-Csv $out -NoTypeInformation -Encoding UTF8
$results | Format-Table -AutoSize

9.2 Script 26.2 — Validação de Telemetria Pós-Execução / Post-Execution Telemetry Validation

# Script 26.2 - Post-Execution Telemetry Validation
param([int]$MinutesBack = 5)
$out = ".\telemetry-validation.csv"
$since = (Get-Date).AddMinutes(-$MinutesBack)
$logs = @(
  @{ Name="ScriptBlock (4104)"; Log="Microsoft-Windows-PowerShell/Operational"; Id=4104 },
  @{ Name="CommandLine (400)"; Log="Microsoft-Windows-PowerShell/Operational"; Id=400 },
  @{ Name="Module (800)"; Log="Microsoft-Windows-PowerShell/Operational"; Id=800 },
  @{ Name="AMSI (1101)"; Log="Microsoft-Windows-Windows Defender/Operational"; Id=1101 }
)
$results = foreach ($l in $logs) {
  $count = (Get-WinEvent -LogName $l.Log -MaxEvents 100 -EA SilentlyContinue | Where-Object { $_.Id -eq $l.Id -and $_.TimeCreated -gt $since }).Count
  [PSCustomObject]@{ Log=$l.Name; EventsLast5Min=$count; Expected=">0" }
}
$results | Export-Csv $out -NoTypeInformation -Encoding UTF8
$results | Format-Table -AutoSize

9.3 Script 26.3 — Deteção de Bypass AMSI / AMSI Bypass Detection

# Script 26.3 - AMSI Bypass Detection
$out = ".\amsi-bypass.csv"
$patterns = @("AmsiScanBuffer", "amsiInitFailed", "AmsiUtils", "amsiContext")
$hits = @()
Get-WinEvent -LogName "Microsoft-Windows-PowerShell/Operational" -MaxEvents 2000 -EA SilentlyContinue |
  Where-Object { $_.Id -eq 4104 } | ForEach-Object {
    foreach ($p in $patterns) {
      if ($_.Message -match $p) { $hits += [PSCustomObject]@{ Time=$_.TimeCreated; Pattern=$p } }
    }
  }
$hits | Export-Csv $out -NoTypeInformation -Encoding UTF8
Write-Host "[+] AMSI bypass indicators: $($hits.Count) -> $out" -ForegroundColor Red

11. Mitigações Blue Team / Mitigations Complementar

  1. Ativar Script Block Logging (4104) — obrigatório para deteção de PowerShell.
  2. Ativar Module Logging (800/4103) — deteta Add-Type e módulos suspeitos.
  3. Ativar Transcription — grava toda a sessão.
  4. Implementar Sysmon — Event ID 1 para process creation com linha de comando.
  5. Monitorizar 1101 (AMSI) — deteta tentativas de bypass.
  6. Correlacionar telemetria — processo + comando + rede é mais forte que cada um isolado.
  7. Alertar sobre downgrade para PowerShell v2 — indicador de evasão.
